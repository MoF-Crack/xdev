## 三、逐项详情

### ① `captureStderr` 46% 输出丢失竞态（**更正 Round 11 误判**）

旧 `restore()`：

```go
os.Stderr = old
_ = w.Close()
_ = r.Close()      // ← 立刻关闭**读端**
```

读端 goroutine 可能还没被调度去读，`r.Close()` 让它带着「已读到的部分」退出，
**管道里剩余数据永久丢失**。

实测：

```
旧实现 300 轮（每轮 3 行）：139 轮丢失（46%）
旧实现 -count=5 连跑：      253 / 265 / 232 / 237 轮丢失（约 80%，每次必红）
新实现 -count=10：           0 丢失
```

修复：`restore()` **只 `w.Close()`**（发 EOF），读端由 goroutine 自己 `defer r.Close()`。

**危害**：这是**测试基础设施**缺陷，但会让 16 个安全相关用例（integrity/HMAC/篡改
检测）随机假绿或假红 —— **假绿会漏掉真篡改**。

守卫：`_NoOutputLossUnderPressure`（300 轮，旧实现下全不丢的概率 ≈10⁻⁷⁷，
因此是**确定性**红）、`_RestoreDoesNotCloseReadEnd`（源码级，剥注释后匹配）、
`_HandlesMultiReadPayload`（64 KiB / 2000 行，钉住「只能读一屏」回归）。

### ② Lua 内存上限：从「判定为不可做」到实现

Round 11 的**正确发现**是：`LState.SetMx` 超限直接 `os.Exit(3)`（一个插件能杀掉
整个 CLI）。**错误的是由此得出「只能等上游」。**

实际可做：看门狗轮询堆占用 → 超限 `cancel()` ctx → `mainLoopWithContext` 在
下一条指令处中断 → 插件线程**真正停下** → 返回普通错误。gopher-lua 确实没有分配
钩子（`newLTable` 直接 `make`），但**不需要**钩子。

实测规模（`archive()` 内）：

```
string.rep 16MiB         5.5ms    16 MiB   无上限
string.rep 64MiB        13.2ms    64 MiB   无上限
200 万次表构造          367.2ms  325 MiB   无上限   ← 很普通的循环
字符串拼接增长           3.0s     10 MiB   （被时间超时兜住）
```

实现要点：
- 默认 64 MiB **堆增长**上限（不是绝对 `HeapAlloc` —— 宿主本身可能已占几百 MiB）。
- `0` = 关闭监控；`XDEV_LUA_MEM_LIMIT_MB` 可覆盖。
- **必须区分内存中止与时间超时**：否则一次 41ms 就被掐掉的调用会报
  `timed out after 10s`，用户以为等了 10 秒且完全看不出真因。现在报
  `Lua memory limit exceeded (8 MiB heap growth)`。
- 时间超时分支**保持原样**（仍含 `timed out`，是仓库既有契约）。

守卫：`_AbortsRunawayAllocation`（核心）、`_ZeroDisablesWatchdog`
（**关键对照**：`limit=0` 时同一循环必须成功，证明拦截确实来自看门狗）、
`_NormalPluginUnaffected`（连跑 3 次）、`_EnvOverride`、`DefaultIsSane`、
`TestWatchMemory_NoGoroutineLeak`、`_ZeroLimitStartsNothing`。

### ④ `.stale-*` 回收补齐两条主路径

Round 11 只挂在 `buildShimIndexMap`，而它**只在重建 shim 索引时才跑**。只用
`xdev use` 切版本、从不安装新 shim 的用户，残留永不回收。

修复：`Activate` / `Uninstall` 成功路径各补一次（best-effort）。

守卫：`TestActivate_ReapsStaleResidue`、`TestUninstall_ReapsStaleResidue`（红→绿已证）、
`_DoesNotReapRealToolDirs`（100 小时前的真实工具目录绝不能被删）、
`_KeepsFreshStaleResidue`（在途保护）。

### ⑤ 诊断错误去掉共享状态

Round 11 的 `lastBuildOptionsErr` 实例字段有**隐含单线程假设**：两个 goroutine
同时调用会互相覆盖 → A 读到 B 的错误。**错误的诊断信息比没有诊断更糟**（把排查
引向无关的工具/版本）。

修复：`BuildDownloadOptionsE` 把诊断作为**第五个返回值**；`BuildDownloadOptions`
保留原签名（CLI 不受影响）；字段删除；`LastDownloadOptionsError()` 标 `Deprecated`
恒返回 nil；GUI 改走 E 版本。

守卫（重写 7 例，新增并发串味用例）：`_ConcurrentCallsDoNotCrossContaminate`
（两 goroutine 各 200 次、不同工具名交替，错误里必须含**自己的**工具名 ——
**旧字段实现下必然失败**，这正是替换设计的根本理由）。

## 七、Round 13 候选

1. **`go test -race` 在本机不可用**（MinGW 8.1.0 对 Go 1.26 race runtime，
   `0xc0000139`）。本轮「并发串味」守卫是靠行为断言（错误里含自己的工具名）抓的，
   **不是** race detector。若能在装有 MSVC / 适配工具链的机器上跑一次 `-race`，
   值得把 `internal/plugin`、`internal/discovery`、`internal/installer` 三个包扫一遍。
2. **Lua 内存看门狗仍是启发式**：20ms 采样间隔意味着「极短时间内的巨量分配」
   （如一次性 `string.rep("x", 2GiB)`）可能在第一次 tick 前就完成。要变成硬保证，
   需要 gopher-lua 层的字节配额（fork vendor）或改用在分配前检查的实现。
   当前默认 64 MiB 对正常插件足够，但**不构成对抗恶意插件的安全边界**。
3. **`ReapStaleResidue` 现在是三处调用**（`buildShimIndexMap` / `Activate` /
   `Uninstall`）。`buildShimIndexMap` 那条已证明会引发递归（Round 11 修复 2b）；
   值得加一个**统一入口**（例如带 `sync.Once` 的定期回收），而不是继续散布调用点。
4. **`BuildDownloadOptions`（四返回值版）现在是纯兼容壳**：全仓生产代码只剩
   `installer.go:626` 一处用它。可以考虑在下一轮把它内联掉，只留 `E` 版本，
   减少「两个版本行为可能分叉」的风险。
5. **junction 长路径矩阵**：本机已覆盖 104–626 字符目标路径并全部通过；
   在未启用 `LongPathsEnabled` 的主机上 >260 字符会被合法拒绝并 **Skip**。
   若 CI 有该配置的机器，值得补跑一次完整矩阵。
