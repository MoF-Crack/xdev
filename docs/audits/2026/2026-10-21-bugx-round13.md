## 三、逐项详情

### ① `.stale-*` 回收：三个调用点 → 一个显式生命周期 + 归档目录

**问题**：`ReapStaleResidue` 有 3 个调用点（`buildShimIndexMap` / `Activate` /
`Uninstall`），其中 `buildShimIndexMap` 那条**已证明会引发无限递归**
（Round 11 修复 2b，全量测试从 1.2 分钟变成 >20 分钟不结束且无任何测试失败）。
**三个调用点等于把同一个地雷铺了三份。**

**做两件事（互为前提）**：

**(a) 扫描恢复纯读** —— 删除 `buildShimIndexMap` 里的回收调用。新增
`StartStaleResidueSweeper` / `StopStaleResidueSweeper`：进程内**唯一**的后台清扫
goroutine（`sync.Once` 幂等、60s 一次），只由 **GUI（长驻宿主）** 启动。
CLI（短命进程）刻意不启 ticker —— 进程在 ticker 触发前就退出了。

**(b) `removeLinkEntry` 的 rename 目标搬到 `current/` 之外（这是根治）**

旧实现 `stale := path + ".stale-" + <nano>`，`path` 是 `current/<tool>` ——
**残留留在 `current/` 里**。这产生一组自相矛盾的需求：

```
回收方要「够旧就删」；而并发写方可能刚 rename 完、正要去 RemoveAll。
为保证不误删在途条目，回收方只能按年龄等 1 小时 ——
于是刚产生的残留必然在 current/ 里停留一小时，
期间它仍是所有扫描方都必须过滤的污染源。
```

搬到 `<xmdeHome>/.stale-residue/` 后矛盾解开：归档里的条目**永远不可能在途**
（写方已放弃它才会搬过去）→ 可立刻安全删；`current/` 从此**根本不会**出现
`.stale-*`。归档路径构造导出为 `shim.ResidueArchivePath`，保证两处同名。
归档目录建不出来时**退回就地改名**（回收绝不能卡住安装）。

**顺带修正一个计数语义 bug**：`ReapStaleResidue` 原返回
`collected + purgedCurrent + purgedArchive`，但第 3 项清的正是第 1 项刚搬进去的
同一批条目 → **同一个残留被算成 2 个**（实测 `reaped 4 ... (archived=2 purged=0
archivePurged=2)` 而实际只有 2 个）。已改为「被处理的不同条目数」，删除量仍在日志。

### ② 内联掉 `BuildDownloadOptions` 四返回值版

它当时已是纯兼容壳，生产代码只剩 1 处调用。**留两个版本就有「行为分叉」的长期
风险** —— 这正是本仓库 Round 8–11 反复出现的失败模式。

删除：四返回值版 `BuildDownloadOptions`、弃用访问器 `LastDownloadOptionsError()`
（当时恒返回 nil）、中间层 `buildDownloadOptionsChecked`。
`BuildDownloadOptionsE` 成为**唯一**公开入口；5 个测试调用点全部迁移。

**顺带的健壮性提升（不是纯重构）**：`downloadWithProgress` 原先
`cacheArchivePath` 预检一次、`BuildDownloadOptions` 内部再算一次，而**后者的错误
被丢弃**（因为它不返回 error）。删除预检改用 E 版后只算一次、错误被真正检查。

### ③ `-race` 不可用 —— 把根因定位到符号级

之前的记录是「MinGW 8.1.0 对 Go 1.26 race runtime，`0xc0000139`」。本轮逐步定位：

1. `-race requires cgo`；本机 `CGO_ENABLED=0`。
2. **没有 MSVC 工具链**：PATH 上的 `clang` 是 xdev 的 shim，指向 LLVM 22，
   但编译失败于 `lld-link: could not open 'libcmt.lib'` / `'oldnames.lib'`
   —— 全盘搜索 `libcmt.lib`：**不存在**。
3. **但本机有 MinGW gcc** `x86_64-w64-mingw32-gcc 8.1.0`（能正常编译+链接）。
   设 `CGO_ENABLED=1 CC=...` 后 **`-race` 能构建**。
4. **运行时 `0xC0000139`**。用 `llvm-objdump -p` 比对系统 DLL 导出表，
   定位到 **3 个符号**：

       WaitOnAddress / WakeByAddressSingle / WakeByAddressAll

   它们是 Windows 8+ 同步原语，实际导出在 **`KernelBase.dll`**
   （`WakeByAddress*` 转发到 `NTDLL`），**不在 `kernel32.dll`**。
   MinGW 8.1 的导入库把它们**静态绑定到 kernel32.dll** → 加载期解析失败。
5. 尝试 `-ldflags=-linkmode=external`：导入表**正确**变成
   `api-ms-win-core-synch-l1-2-0.dll`，但 PE 被判
   `%1 is not a valid Win32 application`（MinGW 8.1 ld 与 Go 1.26 产物不兼容）。

**结论**：现有工具链下无法运行，需要 **MSVC 工具链**（或 MinGW ≥ 11 + 匹配导入库）。
**这是环境限制，不是代码缺陷** —— 如实登记，不假装跑过。

**替代方案（不假装 `-race` 跑过了）**：4 条**确定性**并发守卫，`-count=5` 稳定：
  - 8 goroutine × 15 次交替调用压同一 LState（`e.mu`/`cv.mu` 失守会
    `concurrent map read and map write` 直接 panic，或结果串味）；
  - 8 × 25 次调用后 goroutine 必须回落（Round 12 看门狗的 `stop` 若不生效会累积）；
  - 1 字节上限连压 3 次，**每次都必须失败**（不得出现 cancel 共享状态串味）；
  - 跨包断言 discovery 的并发缓存用例存在（防止唯一防线被删）。

## 四、本轮三次自纠（都值得记）

1. **`.stale-*` 计数翻倍**：修完才发现的语义 bug（同上）。
2. **`ResolveVersion` 返回单个字符串、不是列表**：并发守卫初版按 `len(vs)!=2`
   断言 → 8/8 goroutine 全报错，**看起来像真缺陷**。查签名后确认是**我的断言错**，
   不是产品的并发问题。若不核实，就会把测试 bug 记成「发现并发缺陷」。
3. **`merge_write_d3_test.go` 里的「concurrent」是语义并发**（`concurrentWriteSniffer`），
   没有真实 `go func`。真正有 goroutine 的是 `merge_lock_test.go`。已改指向后者。

另外，两处**源码级守卫**又栽在同一个坑：「判据没排除注释/自身」。
  - `TestBuildDownloadOptions_OnlyOneVersionRemains` 扫描到**自己在断言字符串里
    写的**被禁调用形态；也匹配到**迁移说明注释里**写的字段名。
  - 已分别改为「跳过本文件」与「剥掉 `//` 注释后再匹配」。
  **这是同类错误的第三次复发**（Round 12 `captureStderr`、Round 11
  `InvalidateShimIndex` 都栽在这里），已写进守卫注释。

本轮把 Round 12 列的三条结构性隐患清完了。现在**再开新一轮挖 bug 是合理的** ——
三条「上一轮自己挖的坑」的源头都已处理：

    但**不构成对抗恶意插件的安全边界**。
  - **`-race` 需要 MSVC 工具链**。若日后装上 VS Build Tools，直接
    `CGO_ENABLED=1 go test -race ./internal/plugin/ ./internal/discovery/ ./internal/installer/` 即可。
