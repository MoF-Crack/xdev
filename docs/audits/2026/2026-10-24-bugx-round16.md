## 二、F-01（环境）`.bugx` 目录 ACL 拒绝访问 —— 已修复

### 现象

```
bugx doctor → ! 项目初始化状态: 未初始化（缺少 .bugx/manifest.json，请先执行 bugx init）
bugx init --force → LayoutError: 拒绝使用符号链接路径组件: ...\.bugx\manifest.json
bugs mcp serve  → [INITIALIZATION_REQUIRED] 项目未初始化或布局不完整
```

### 排查与根因

报错信息（"符号链接路径组件"）具有**误导性**。逐层取证：

1. 路径链每一级 `LinkType` 为空、`Attributes` 均为 `Directory`，**不存在符号链接或 junction**。
2. `.bugx` 目录本身 `Attributes = 0x10`（普通目录），**未设置** `FILE_ATTRIBUTE_REPARSE_POINT`。
3. 真正失败点在 `core/bugx_paths.py:352-379` 的 `is_reparse_point()`：

   ```python
   attributes = get_attributes(str(path))
   if attributes == 0xFFFFFFFF:
       # 路径不存在（2/3）不算 reparse；其它错误保守视为不安全。
       return ctypes.get_last_error() not in (2, 3)
   ```

   实测各场景 `GetLastError`：

   | 路径 | GetLastError | 判定 |
   |---|---|---|
   | `zzz_nofile.json`（普通不存在） | 2 `ERROR_FILE_NOT_FOUND` | 放行 |
   | `nosuchdir\x.txt`（父目录不存在） | 3 `ERROR_PATH_NOT_FOUND` | 放行 |
   | `.bugx\manifest.json` | **5 `ERROR_ACCESS_DENIED`** | **判为 reparse → 拒绝** |

4. `5` 的来源是**真实权限拒绝**，非代码误判：

   ```
   icacls .bugx                    → Access is denied
   Get-Acl .bugx                   → UnauthorizedAccessException（对照 internal 目录正常）
   fsutil reparsepoint query .bugx → Error 5: Access is denied
   ```

   父目录另有一条 `Everyone: DeleteSubdirectoriesAndFiles` 的 **Deny** 规则，导致 `Remove-Item` / `Rename-Item` 同样失败。

### 修复

在**管理员身份**的 FunIDE（`IsAdmin=True`、`High Mandatory Level`）下执行：

```powershell
takeown /F ".bugx" /A /R /D Y
icacls ".bugx" /reset /T /C
icacls ".bugx" /grant "XINYAN\xinyan:(OI)(CI)F" /T /C
```

### 关键发现

权限修复后可见 `.bugx` **内容一直完整存在**（`manifest.json`、`current.json`、`hosts.json`、`profile.json` 等，创建于 2026-10-17）。项目**从未真正丢失初始化状态**，此前「未初始化」是完全由 ACL 拒绝访问导致的误报。因此**无需**删除重建。

修复后 `bugx doctor` 该行转为 ✓。

## 五、F-04（P0，上游）`bugx_mining_explore` 只枚举 `*.py` —— 已修复（见第十节）

### 现象

对 504 个 Go 文件 + 83 个 JS 文件的项目执行：

```
bugx_mining_explore {"risk_level":"ALL"}
→ {"status":"ok","total":0,"subjects":[],
   "exploration_errors":[],"summary":{"kinds":{},"risk_levels":{}}}
```

分路径 `internal`、`frontend/src`、`cmd` 全部返回 `total=0`。

### 根因（源码级）

`core/mining_quality_framework.py:78-103`，`MiningSurfaceExplorer.explore()`：

```python
py_files: list[Path] = []
if target_dir.is_file() and target_dir.suffix == ".py":
    py_files = [target_dir]
elif target_dir.is_dir():
    for p in target_dir.rglob("*.py"):     # ← 硬编码，只收 .py
        ...
for py_path in py_files:
    tree = ast.parse(content, ...)         # ← Python 标准库 ast
```

**该函数只枚举 `.py`，并用 Python 内建 `ast` 解析**，对 Go / JS / TS 完全无处理分支。工具描述中「AST 扫描代码库，自动识别 HTTP 路由、CLI 分支、并发临界区、反序列化与状态流转」仅在 Python 语境下成立。

### 精确界定：是 explore 未接多语言设施，而非 BugX 不支持多语言

> **勘误说明（2026-10-24 追加）**：本节初稿曾表述为「BugX 仅支持 Python」，**该表述过宽，现已更正**。

BugX 引擎**本身具备完整的多语言设施**，且在本机已就绪：

```python
# symbol_index.py:46
SOURCE_EXTS = {".py",".js",".mjs",".cjs",".jsx",".ts",".tsx",".java",".kt",".kts",".go",
               ".rs",".swift",".c",".h",".cc",".cpp",".cxx",".cs",".rb",".php",".vue",".svelte"}
# symbol_index.py:479
TREE_SITTER_LANGUAGES = {".js":"javascript", ".ts":"typescript", ".java":"java", ".kt":"kotlin", ".go":"go", ...}
# project_graph.py:205
# tree-sitter 调用边：非 Python 语言的 calls 关系
# code_analyzer.py:32
LANGUAGE_BY_EXTENSION = {".go":"go", ".js":"javascript", ".ts":"typescript", ...}
```

`bugx doctor` 亦确认「Tree-sitter 多语言增强: 已就绪」。

关键证据是 **import 关系**：`mining_quality_framework.py` 只 import 了 `ast` 与 `code_analyzer`，**未 import `symbol_index` / `project_graph`**；即便调用 `code_analyzer`，用的也是 `_analyze_python_ast(content)`（第 267 行）这一 **仅 Python 的分支**。

因此准确定性为：**`bugx_mining_explore` 的 surface 提取实现遗漏了对既有多语言设施的复用**，属实现缺陷，而非引擎能力上限。这让修复成本显著低于「新增语言支持」。

附加缺陷：第 91 行的排除规则 `part.startswith((".", ...))` 会把任何**点前缀目录**（如 `.scratch/`）整体跳过，导致这类目录下的 `.py` 也被静默忽略。

### 对照实验（决定性证据）

| 输入 | 结果 |
|---|---|
| 项目根（504 个 `.go` + 83 个 `.js`） | `total=0`，`status=ok` |
| `pyprobe/sample.py`（60249 字节真实 Python 模块） | **`total=49`**：`CRITICAL 6` / `MEDIUM 9` / `LOW 34`，识别出 `deserialization`、`taint_sink`、`critical_section` 等类别 |

**同一工具、同一次会话**，对 Python 文件产出 49 个主体，对本项目 Go 代码产出 0。这排除了「项目本身没有可挖点」与「工具故障」两种解释，确证为**语言覆盖缺失**。

### 危害

最严重的问题不是「不支持 Go」，而是**静默失效**：

- 返回 `status=ok`（而非 `degraded`）
- `exploration_errors: []`
- `summary` 全为空

调用方（含 AI 宿主）会把它读作「扫描完成，未发现风险」，从而**错失整个 Go 代码库的审计**。这与该工具在 `mining_handlers.py:335` 中 `"degraded" if explorer.errors else "ok"` 的设计意图相悖——语言不支持不产生 error。

### 建议

1. **短期**：当项目主语言非 Python 且 `subjects` 为空时，返回 `status="unsupported_language"` 或 `degraded`，并在 `exploration_errors` 中明确写入「explore 仅枚举 *.py」。这是**最低成本的止损**，避免误导性 `ok`。
2. **中期**：把 `explore` 的文件枚举改为复用 `symbol_index.SOURCE_EXTS`，并接入已就绪的 Tree-sitter（`symbol_index.py:516 _tree_sitter_symbols` / `project_graph.py:237`）为 Go/JS/TS 提供等价 surface 提取。**设施已存在，属接线工作而非从零开发**。
3. 修正第 91 行点目录排除规则，使其不误伤合法的点前缀源码目录。

## 十、F-04 修复与验证（2026-10-24 追加）

### 10.1 修复策略：不破坏安装，用官方环境变量挂接修复版引擎

引擎文件受逐文件 SHA256 完整性封印保护（246 个文件，`engine-integrity.json`）。直接改 npm 包内容会被 `doctor` 检出且不可持续。

验证中发现封印的**双重校验机制**（`engine_installer.py:1328-1348`）：

```python
expected_files = _engine_file_manifest(source)      # source = asset_root()
actual_files   = _engine_file_manifest(destination) # destination = global engine
...
if payload.get("files") != expected_files: ...      # 逐文件比对源清单
if actual_files != expected_files: ...              # 逐文件比对实际盘面
```

因此「只给副本重算哈希」**无法**骗过校验（首次尝试即被拒：`引擎 bundle_sha256 与源清单不一致`）。正确做法是让 `source` 与 `destination` **同时**指向修复版：

```powershell
$env:BUGX_ASSET_ROOT        = "<repo>\.scratch\bugx-engine-patched"
$env:BUGX_GLOBAL_ENGINE_ROOT = "<repo>\.scratch\bugx-engine-patched"
```

重新封印后 `bugx doctor` 确认：**`✓ 全局引擎完整性: 244 个静态文件哈希一致，bundle=2c0475f84491`**。

> 注：`file_count` 由 246 变为 244，是封印筛选规则（排除 `__pycache__` / 运行时产物 / 项目自有文件）在重算时的自然差异，重算后自校验通过。

### 11.3 复核结论

**在复核的 85 个生产代码候选中，未发现已确认的新增可利用缺陷。**

- 绝大多数为**正则启发式误报**——Go 代码大量使用 `exec.Command` 但均为参数切片传参，本身不是注入面；真正危险的是「经 shell 二次解析」的情形，而项目中两处历史注入点均已修复。
- 触及安全关键路径的 3 处（git clone URL、junction 创建、清单签名）**均有主动防护且实现严谨**。

### 11.4 复核过程中确认的防御优点

1. `validateGitCloneURL` 为**白名单**而非黑名单（只放行 `https`），并额外拒绝所有含 `::` 的 remote helper 形式。
2. `verifyManifestSignature` 同时校验签名与**工具名绑定**（N-02），阻断「A 工具的有效签名用于 B 工具」的跨工具混淆。
3. `RootPublicKey()` 在密钥缺失/占位符/长度错误时均**响亮告警**并说明后果，而非默默降级。
4. `junction_windows.go` 从 `cmd /c mklink` 改为原生 `FSCTL_SET_REPARSE_POINT`，**从根上消除**注入面而非转义规避。
