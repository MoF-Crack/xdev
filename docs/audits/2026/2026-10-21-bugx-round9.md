### 几个值得单独记录的

**A-10（P1，本轮最高价值）**：`AtomicWriteFile` 是 16 个调用点、8 个包的共享底层
（config 的 home 缓存、manifest 的文本级改写、discovery 的 sniff 缓存、isolator 的
隔离状态、shim 索引、signer/sign_manifest…）。固定 `.tmp` 下两个并发写者共享同一个
中间文件：

- **跨写者内容污染**：A 写 `tmp("AAAA")`、B 写 `tmp("BBBB")`、A 执行 rename
  → 目标内容是 `"BBBB"`（**A 发布了 B 的字节**）；
- **大量并发失败**：本机实测 16 写者 × 40 轮 = **610 次**失败。

修复后并发守卫实测 **污染 0**。守卫设计上有一处必须记录的方法论：
`CreateTemp` + 裸 `os.Rename` 仍会出现 `Access is denied` —— 那是 **Windows 目标竞争**
（与中间文件是否唯名无关，实测证明：把 rename 换回裸调用、保留 CreateTemp，失败照旧）。
因此终版守卫**只判定污染为 0**，不断言「零失败」；这与仓库既有先例
`internal/config/atomicwrite_convergence_test.go:151-160` 的口径一致。
**这条区分很重要**：把两类失败混在一起会让守卫在负载抖动下假红，也会误判修复无效。

**A-11（P1）**：`AcquireFileLock` 是 OS 字节范围锁（`LockFileEx`/`flock`），**不可重入**。
嵌套调用时内层阻塞满 10s 超时，然后走 `err != nil` 分支 → 记 WARN 并
`return fn()` → 内层临界区**完全没有跨进程序列化**（正是票 10/44 要防的 PATH 丢写），
外加 GUI 假死 10s（实测 `elapsed=10.08s`）。

修复者做了一次**很值得肯定的区分**：只拦截**同 goroutine** 的嵌套（外层已持锁，
内层直接执行仍保持保证），同进程**其它 goroutine** 保持原语义不动 —— 因为实测那条
路径是**真正的跨临界区竞争**（两次 300ms 临界区共 604ms，即第二者等完了第一者，
而非 10s 超时），10s-then-degrade 契约被既有守卫依赖。

**A-15（P2）的取舍必须记录**：把 `xmdevenv_dir` 纳入 HMAC 会**改变 HMAC 值**，
升级前写下的配置文件必然验签失败一次。修复**没有**为了平滑升级而接受旧格式 HMAC
（那恰好会放过「只篡改 `xmdevenv_dir`」这一攻击，让修复完全失效），而是保持既有的
「告警 + 重置敏感字段 + 清空 Integrity、**不拒绝启动**」契约，并用
`TestIntegrityHMAC_LegacyConfigUpgradeIsNotFatal` 显式构造升级场景钉死「不锁死用户」。
代价是自定义过的派生目录会在这一次重置中回到 `<root>/<name>` —— 已在测试注释里写明。

**P2-6（P2）**：F-12 让 `.part` 按 URL 分代，「不同 URL 互不干扰」成立；但**同一个 URL**
重新发布内容（nightly / 重打 tag / CDN 回源换对象）时代际键不变，旧内容前缀会与
**新内容**后缀拼成一份文件。审计实测：本地残留 = 旧内容前 2048 字节，服务端同 URL
返回新内容（同长度）→ `err=nil`、拼接结果被接受并写 **TOFU pin** → 后续安装都基于
坏文件、只能手动删缓存恢复。
修复为两层：标准 `If-Range`（弱 ETag 按 RFC 9110 退回 `Last-Modified`）+ 拿到 206 后
**本地再比对一次校验器**（`If-Range` 依赖服务端合规，非合规实现仍会回 206）。
不一致即删 `.part` + `.meta` 并 fail closed。守卫红→绿已证：禁用本地校验即复现
「`err=nil` 且落盘 4096 字节拼接内容」。

### P0-1：A-01 的**写侧**从未闭合 —— `L.SetGlobal` 仍是裸调用

- **位置**：`internal/plugin/vfox_compat.go:159`
- 这是本轮最值得记录的一条，因为它精确命中了本轮的元命题：**A-01 修了「读」没修「写」**。
  A-01（Round 8 P0）把 `GetGlobal`/`GetField` 包进了 `extractField → L.PCall`，
  但把 `PLUGIN.available/archive/...` 提升为全局用的是 `L.SetGlobal` —— 而
  gopher-lua 的 `SetGlobal → setFieldString` 在**键不存在**时会执行 `__newindex`。
- **实测**：`LoadPlugin` 直接 Go panic（`newindex-boom:available`），进程 exit 2。
- **放大点与 A-01 完全一样：不需要恶意。** 插件作者用 `__newindex` 抓「严格全局变量」
  或拼写错误这种良性写法，同样打崩 CLI/TUI/GUI 的**每一次启动**
  （`registerUserPlugins` 在 `RegisterAll` 里加载每个用户插件）。
- 即使 `__newindex` 只吞掉写入也危险：全局没写进去 → 误报 "available() function not found"。
- **修复**：改用 `globals.RawSetString`（绕过元方法直接写 globals 表），既避免 panic
  又保证写入生效。红→绿已证（回退即复现审计的原始 panic 消息）。

### P1 级（本轮已修 3 项）

**P1-1（安全）junction 创建经 cmd.exe 的**命令注入** —— 本轮的第二个高价值发现。

`CreateJunction` 用 `exec.Command("cmd", "/c", "mklink", "/J", link, target)`。
`os/exec` 在 Windows 上只对「含空格/制表符/引号」的参数加双引号，而 **cmd.exe 会再解析
一遍命令行** —— `&` 是合法的文件名字符，于是含 `&` 的 tool name / version / 安装根目录
会把 mklink 参数切成多条命令，构成 **manifest 可控的任意命令执行**。

审计实测（PATH 上放一个写 marker 的 `probe.exe`）：
```
Activate(tool="inj&probe&", ver="1.0.0")   → err=nil, marker=true
Activate(tool="verinj", ver="1.0&probe&")  → err=nil, marker=true
cmd 同时报 '.tmp-…' 不是内部或外部命令（参数确实被切断）
```
tool name 与 version 都是 manifest 字段（第三方 manifest、Lua 插件、被嗅探器写入的
远端 tag），且注入发生在**激活阶段、先于任何二进制执行**。

同一根因还有**功能性**后果：XMDEV_HOME 含 `&`（如 `D:\Tools & SDKs`）时 junction 一律
创建失败 —— 在没有 symlink 特权的主机上激活永久失败。

修复两层：① 自行构造命令行经 `SysProcAttr.CmdLine` 传入并为每个路径加双引号
（cmd 在引号内把 `& | < > ^ ( )` 当字面量，同时修好功能性问题）；② 拒绝无法安全表达的
字符（`"`、`%`、`!`、控制字符、空路径）。实现拆到平台专属文件
（`junction_windows.go` / `junction_other.go`），`fs.go` 只做委派。
**未采用**原生 `FSCTL_SET_REPARSE_POINT`：仓库注释记载手写 `REPARSE_DATA_BUFFER` 曾在
不同路径长度下脆弱并被回退过（Spec 032），在无法充分回归路径长度矩阵前重写有让**所有
安装失败**的风险 —— 列为 Round 10 独立项。

**P1-1 `SanitizeURL` 在 `url.Parse` 失败时原样返回** —— Round 8 P1-4 的残留（另一车道）。
「解析失败」恰是最需要脱敏、也**必然出现**在同一错误链里的场景：`IsSafeExternalURL`
的 "invalid URL" 错误本身就是 `url.Parse` 的 `*url.Error`，文本内嵌整段原始 URL。
实测 `%zz` 转义错、坏端口 `:bad`、控制字符三种形态的 userinfo 与 `?token=` 全部原样
出现；对照（可解析但被策略拒绝）已正确脱敏。修复：解析失败与无 scheme 时退化为
**正则文本脱敏**。
同批补 **P2-4**：downloader 3 处 + remote 1 处日志用 `%v`/`%s` 直出，绕过同文件现成的
`sanitizedReason`；实测 `?token=TOPSECRET123` 原样进日志（预签名 URL 会被贴进 issue）。

**P1-3 4 段版本完全无法解析 —— 影响 5 个真实 manifest。**
`parseSemver` 用 `SplitN(s, ".", 3)` → `"2026.2.0.1"` 的第 3 段变成 `"0.1"`、Atoi 失败。
实测（与 installer 安装入口同一函数）：
```
clion@"latest"     -> "2026.2.0.1"   ✓
clion@"2026.2.0.1" -> ""             ✗ unrecognised version spec
clion@"^2026"      -> "2026.2"       ← 静默降级到较旧版本
```
而 `filterVersions` **静默丢弃**解析不了的条目 → 范围解析永远选不到 4 段构建。
真实语料：clion/goland/webstorm 的 latest 就是 `2026.2.0.1`；
jetbrains-idea-community `2025.2.6.3`、pycharm-community `2025.2.6.2`。
**与 R8-2 同一失败形态**（「以为在更新，其实没推上去」）。
修复：`semver` 增 `extra []int`，`parseSemver` 接受任意段数，`compare` 在 patch 后、
pre-release 前比较 extra（缺失段视为 0）。

### P2 级与本轮修复的关系（含我自己修复的缺口）

**P2-1（我自己的缺口）P2-6 的本地校验只写在 206 分支，416 提升路径照样把旧内容固化。**
416 分支只靠 `completePartResidue` 的「长度 == total」就放行 —— 而「长度相等」不是
「内容相同」的证据。同 URL 换内容且新旧同长度时，本地满长的**旧内容**被当新归档 rename
并写 TOFU pin；**客户端手里已有反证**（响应 ETag 与本地记录不同）却没用。属修复缺口。
已补齐：416 提升前做同一校验器比对，不一致即删 `.part`+`.meta` 并 fail closed。

**P2-3 强/弱 ETag 比较与 RFC 弱比较语义相反**：`ifRange()` 正确排除了弱 ETag，但
`matchesResponse` 仍逐字节比较 → 服务端在同一内容上切换强弱形态时误判「内容已变」并
误删可续传前缀。已改为 RFC 9110 §8.8.3.2 的弱比较。

**P2-2 `yamlScalarFor` 不转义控制字符（A-17 残留）**：`needsYAMLQuoting` 对 `\n\r\t`
返回 true（加引号），却**没有转义** → 拼出 `"a<真实换行>b"`，而 YAML 双引号标量跨行会被
**折叠成空格**：文件合法、值变了（实测 `latest` `"1.0.0\n2.0.0"` 往返成 `"1.0.0 2.0.0"`）；
NUL 则直接产出**不可解析**文件。已修（`\n\r\t` 与其余 `<0x20` 用 `\xNN`；单引号原值遇
控制字符切双引号形态）。

## 四、未修项（Round 10 首批，按风险排序）

1. **P1-2 Windows 命名互斥量线程亲和 → 20% 的激活漏释放跨进程锁**（本轮未修，最高优先）。
   goroutine 阻塞后会迁移到别的 OS 线程，`ReleaseMutex` 以 `ERROR_NOT_OWNER` 失败，而
   `CloseHandle` **不释放所有权** —— 只要另一进程正等待（持有句柄使内核对象存活），该
   mutex 会一直被原线程占有到线程退出。
   审计实测：30 次 `Activate` 中 **6 次漏释放（20%）**；跨进程确定性对照
   `... is locked by another xdev process (timeout after 3s) elapsed=3.0148s`，同线程
   Release 对照 `elapsed=302.97ms`；所有权判定 `WaitForSingleObject(400ms)` 超时
   `wr=258`。后果：GUI 常驻 + CLI 并发时，CLI 对同一工具的 install **每次阻塞 5 分钟**
   再失败、`xdev use` 每次 30 秒，直到 GUI 退出。修复方向：改用
   `util.AcquireFileLock`（LockFileEx，非线程亲和）或 `CreateSemaphore`。
   **未修原因**：这动的是安装链路的核心锁原语，需独立改动 + 跨进程回归矩阵，
   不宜在本轮末尾仓促改。
2. **P1-1/P1-2（Lua 资源耗尽）**：M-12 的超时只守住 `L.CallByParam`，**守不住结果提取**
   （`extractField`/`getField*` 的 `L.GetField` 会执行插件给的 `__index`，`while true do end`
   → 永久挂起；实测超时设为 400ms 却跑了 7.43s）**与插件加载**（`L.DoFile` 裸调用；
   实测超时 100ms 却跑了 2.97s）。任意 `$XMDEV_HOME/plugins/x.lua` 的顶层死循环

### P1：`update/policy.go writeJSONAtomic` 是第三份实现，漏了 rename 重试

- **位置**：`internal/update/policy.go:170`（修复前裸 `os.Rename`）
- **实测**：12 写者 × 60 轮 + 6 并发读者 → **696/720（96.7%）失败**；
  同构压测走 `util.AtomicWriteFile` 为 **0 失败**（434 次瞬态冲突被 ~55ms 重试吸收）。
- **瞬态性证明**：首次尝试 **563.7µs 即失败**，释放句柄后**同一次** rename 成功。
- **影响**：自我更新节流缓存写不进去 → 每次启动都重查远端，可能触发 API 限流。
- **修复**：`renameWithRetry`（10 次 / 1..10ms）；**未**朴素替换成
  `util.AtomicWriteFile` —— 本函数用 `json.NewEncoder`（多一个尾换行）且自己
  `MkdirAll` 父目录，两者行为不同（已加守卫钉住换行语义）。
- **守卫**：`TestWriteJSONAtomic_TransientlyBusyTargetIsRetried` 是**确定性**的 ——
  Windows 上 Go 的 `os.Open` 不含 `FILE_SHARE_DELETE`，持读句柄可确定性阻塞 rename，
  10ms 后释放；有重试→PASS，裸 rename→微秒级失败。红→绿已证。

### P2：PATH 只有上界守卫、没有下界 → 可把用户 PATH 写成空值

- **位置**：`internal/env/win_path_windows.go` 的 `WriteUserPath`（只判 `>32767`）
