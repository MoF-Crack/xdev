## 三、逐项详情

### P3-7 `ActiveVersion` 悬空链接 → 连带发现 `Uninstall` 的顺序依赖

`fs.go` 只做 `os.Readlink`，从不检查目标是否存在。F-23 场景（解压失败后
`RemoveAll(install/<tool>/<ver>)`）会让 `current/<tool>` 悬空，而 `ActiveVersion`
仍报「已激活」→ `xdev current`、`IsUpgradeAvailable`、GUI `GetActiveVersion`、`doctor`、
`profile` 全都看到**幻影**版本。

修复：`Readlink` 后 `os.Stat`（**跟随**链接，确认目标存在）。`ActiveInstallPath` 同源。

**🔴 连带发现**：修好后 `TestUninstall_ActivatedVersion_RepointsFast` 与
`_LastVersion_RemovesLink` 立刻变红。排查结论是 `Uninstall` **一直依赖那个幻影行为**：

```
1. os.RemoveAll(target)                    // 先删掉 install/<tool>/<ver>
2. activeVer, _ := i.currentVersion(...)   // 再读活跃版本 ← 此时链接已悬空
3. if activeVer == ver { 重指向 / 清理 shim 与环境变量 }
```

第 2 步能工作**只因为** `ActiveVersion` 不检查目标。修复后它正确返回 `("", false)`，
于是卸载活跃版本**既不重指向也不清理**，`current/<tool>` 永久悬空（比原缺陷更糟）。
修复：把 `currentVersion` 提到 `RemoveAll` **之前**。

### `SafeName`：纯点/空格放行 + 保留名误报

**缺陷一**：尾随点检查写成 `if trimmed != s && trimmed != ""` —— 那个 `!= ""` 让
**全点/全空格**名字（`"..."`、`"   "`、`". ."`）恰好经 TrimRight 变成空串而被**放行**。
旧注释声称这类名字「caught by "." check above」，但上面只拦精确的 `"."`/`".."`。

**缺陷二（Round 10 同一错误的漏网处）**：保留名用「剥掉第一个 `.` 之前的部分」比对，
把 `con.txt`/`nul.txt`/`aux.x.y`/`con.txt.bak`/`lpt9.txt` 全判非法。本机实测（`os.WriteFile`
+ `os.ReadDir`）证明它们都是**合法真实文件**；只有裸 `NUL`/`con` 才是设备名。

修复：纯点/空格改为 `TrimRight(s,". ")==""` 即拒绝；保留名改为**整体相等**。
`..foo`/`...x`/`.hidden` 这类「以点开头但非纯点」仍放行（Round 10 已确立合法）。

### `SniffAll` 吞掉合并写失败（待办 8）

`withCacheLock` 在缓存损坏时**正确地**返回错误并拒绝写空缓存（Round 10 P2-1），
但调用方**只 log 不返回** → `xdev sniff --all` / GUI「全部嗅探」**显示成功**，而这一轮
结果**一个字节都没落盘**。这是 F-56「读失败绝不覆写」的**另一半**。

修复：把 `mergeErr` 并入 `errs` 上报。**与 Round 10 P2-2（isolator `saveState` 吞错）
完全相同的形态** —— 修 A-02 的写侧时修了 isolator，discovery 这里漏了。

### CLI 吞掉 `Shutdown()` 错误（待办 6）

Round 10 把 `Scheduler.Shutdown()` 改成返回 `error`，但 CLI 调用方仍忽略返回值。
修复：`ShutdownSniffScheduler() error` 外传；`main.go` 写 stderr，**刻意不改退出码**
（票 33 契约：退出码反映子进程真实退出码）。

新增测试接缝 `Scheduler.SetStartupStateForTest` —— 跨包守卫需要手工搭出「嗅探仍在飞行」
的状态才能确定性地驱动兜底写盘分支。

### `.stale-*` 按年龄回收（待办 3）+ 自查抓到的无限递归

Round 10 只做了过滤，残留永久占着 `current/`。修复：新增 `shim.ReapStaleResidue`，
按年龄（默认 1 小时，可注入）回收，并在 `buildShimIndexMap` 里顺带调用。

**按年龄而非无条件删**：`removeLinkEntry` 是「先 rename 再 RemoveAll」，中间那一瞬
`.stale-*` 是**活着的临时名**；GUI 与 CLI 并发时无条件删会抽走另一个进程正在删的目录。

**🔴 本轮自查抓到的自己引入的无限递归**：

```
buildShimIndexMap → ReapStaleResidue → InvalidateShimIndex
→ writeDiskShimIndex → (内存索引为 nil 时) buildShimIndexMap → …
```

**症状极具迷惑性**：全量 `go test ./...` 从 **1.2 分钟变成 >20 分钟仍未结束**，
而且**没有任何一条测试失败**（不是栈溢出 —— 每次递归都在做真实的目录遍历 + 文件写，
只是永远不返回）。靠「跑一遍看有没有红」完全抓不到。

修复：删掉那次 `InvalidateShimIndex` 调用（残留本来就不进索引，删掉它们不改变索引内容）。

### GUI 的 "empty destination"（待办 7）

`BuildDownloadOptions` 不返回 error（四处调用点直接消费四个返回值），缓存路径不安全时
把 dest 置空（**fail closed 是对的**），但原因被丢弃 → 用户只看到
`"empty destination"`，无法定位是工具名、版本号还是 format 非法。

修复：`Installer` 增加 `lastBuildOptionsErr` + `LastDownloadOptionsError()` 访问器
（**开头重置**，否则「旁路字段」会让一次正常下载读到陈旧错误）；GUI 在 `dest==""` 时
读回并 `%w` 包装。fail-closed 契约不变。

### Lua 资源耗尽（待办 1/2）—— 尾递归已界定，内存上限证伪

**关键发现**：gopher-lua 的 `LState.SetContext` 把主循环切到 `mainLoopWithContext`，
在**每条指令**前检查 `ctx.Done()`。实测：`callTimeout` 设 30 秒、ctx 设 300 毫秒
→ **0.63 秒**返回 `context deadline exceeded`。

修复：新增 `runWithContext`，三个调用点（`callAvailable`/`callArchive`/`callEnvVars`）
全部改用。**保留** `callProtected` 的 goroutine（它负责把 panic 转成错误，ctx 做不到）。
调用结束后恢复 `L.Context()`（否则同一 VM 下一次调用会带着过期 ctx 立即失败）。

**尾递归**（Round 10 实测「5 分钟未返回、只能 kill」）：现在 **350ms** 内被中断。

**内存上限：证伪为不可用，保持未实现。** `LState.SetMx` 的实现是一个后台 goroutine
轮询 `runtime.ReadMemStats`，超限直接 **`os.Exit(3)`**。让宿主进程因为一个插件的内存
用量而退出，比超时**更糟** —— 一个失控插件可以把整个 CLI 杀掉。实测现状：
`string.rep("x",16MiB)` 在 5.02ms 内成功、堆增长 16.8 MiB，**无上限**。需要 gopher-lua
层的字节配额支持或 fork。

### 原生 junction 迁移（待办 4）

Round 9/10 都列为「应作为独立改动 + 配足路径长度回归矩阵」（仓库注释记载 Spec 032
曾因手写 `REPARSE_DATA_BUFFER` 在不同路径长度下脆弱而被回退）。本轮补齐矩阵后迁移。

**🔴 我亲手复现了 Spec 032 的那个坑**：矩阵首跑**全部 16 个用例一起红**，
错误 `The data present in the reparse point buffer is invalid`。

我没有靠重读文档去蒙，而是**用真实 mklink 造一个 junction，再用
`FSCTL_GET_REPARSE_POINT` 把 buffer 逐字节 dump 出来**当基准：

```
[00] 03 00 00 a0   ReparseTag = 0xA0000003
[04] ec 00         ReparseDataLength = 236
[10] 74 00         SubstituteNameLength = 116  (= 58 字符 × 2)
[12] 76 00         PrintNameOffset      = 118  ← **= 116 + 2**
[14] 6c 00         PrintNameLength      = 108
```

根因：**`PrintNameOffset` 必须跳过 Substitute 的 NUL 终止符**（`substBytes + 2`）。
我初版写成 `substBytes`，指向了那个 NUL 本身。

这恰好解释了 Spec 032 当年为什么「时好时坏」：长度字段必须是**字节数**（字符数×2），
而 `PrintNameOffset` 还额外要 `+2`。纯 ASCII 短路径下写错也可能侥幸建出来，
长路径/非 ASCII 立刻失败。

**顺带收益**：不经 cmd.exe 后，`%` / `!` / `&` / `^` / `( )` 这些在文件名里合法的字符
不再需要被拒绝 —— Round 9/10 下 `D:\100%Portable` 这类安装根目录**根本无法激活**。

## 四、三处「测试自身」的教训

1. **`ShutdownSniffScheduler` 行为用例初版假绿**：`Shutdown` 的第一个 select 在
   `startupDone` 已关闭时直接 `return nil`（不碰磁盘），所以 `NewScheduler` 之后直接调用
   根本走不到兜底写盘分支。**错误路径的守卫必须确认「真的走到了那条分支」。**
2. **Lua 超时守卫初版假绿**：断言「超时后返回了 `timed out` 错误」在修复前后**都成立**
   （旧实现也返回错误，只是把 goroutine 丢在那里继续跑）。唯一能区分的信号是
   **那个 goroutine 还在不在**。实测对照：旧实现等待 2 秒后 goroutine 仍为 4（before=3）
   → 红；新实现立刻回落 → 绿。
3. **`SniffAll` 用例初版单条跑 75 秒**：没注入空 catalog，于是去嗅探真实 manifest 里的
   全部工具（且依赖网络）。改用既有的 `s.loadCatalog` 接缝注入空 catalog 后降到
   **0.02 秒**。

## 七、Round 12 候选

1. **Lua 内存配额**：需 gopher-lua 层支持（`SetMx` 不可用 —— 它 `os.Exit(3)`）。
   可选路径：fork vendor 的 gopher-lua 加字节计数，或改用支持配额的 Lua 实现。
2. **`internal/config` 的负载敏感用例**：`TestIntegrityHMAC_CoversMirrorPreference`
   在高并发下偶发失败，值得查清是共享临时目录还是时序问题。
3. **junction 的长路径矩阵在未启用 LongPathsEnabled 的主机上会 Skip** ——
   值得在一个启用了长路径的机器上补跑一次完整矩阵。
4. **`ReapStaleResidue` 只挂在 `buildShimIndexMap` 上**：若某用户长期不触发 shim 索引
   重建，残留不会被回收。可考虑在 `Activate`/`Uninstall` 成功后也调用一次。
5. **`LastDownloadOptionsError` 是「最近一次」语义** —— 多 goroutine 并发调用
   `BuildDownloadOptions` 时会互相覆盖。目前 GUI 单线程调用，但值得加注释或改为
   返回值的第五个分量（会波及四处调用点）。
