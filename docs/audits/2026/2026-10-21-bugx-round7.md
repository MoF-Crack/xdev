## 三、发现详情

（完整取证链见 `.scratch/bugx-round7/findings-verified.md`）

### F-01（P1）GUI 测试接缝自死锁

- **位置**：`internal/gui/app_env_vars_percent_test.go:80-92` × `internal/gui/app_env_vars.go:507-524`
- **根因**：`store.mu` 是不可重入的 `sync.Mutex`。测试接缝持 `store.mu` 调用 `transform`，而 transform 闭包内 `percentExpander.lookup` 的**惰性加载**会再次进入 `mergedEnvSnapshotFn` → 同 goroutine 二次加锁 → 永久阻塞。
- **影响**：`internal/gui` 整包 606s 超时；CI 门禁变红。生产侧不受影响（生产持的是文件锁 `withUserPathLock`，无重入）。
- **归因**：`git show HEAD:internal/gui/app_env_vars.go | grep -c envTransformPathFn` → `0`，证明由未提交的票 44 改动引入。
- **修复**：进入 transform 前先 `exp.lookup("")` 预热快照，消除闭包内首次加载。
- **验证**：修复前定向用例 `panic: test timed out after 40s`；修复后 `ok 1.584s`、整包 `ok 16.574s`；**回退该行即复现超时**（证明是该行的充分修复）。真实树全量 `go test ./... -short -count=1` → **31 包全绿，exit 0**。

### F-04（P2）PATH 清理的虚假成功回报

- **位置**：`internal/gui/app_env_vars.go:644-650`（按回读值推断动作）
- **根因**：票 44 将「PATH 全部条目失效」改为保留原值（不写不删，返回 nil），但批量入口仍以「回读非空 ⇒ 已清理」推断动作 → 实际零改动却上报 `Action="cleaned"` / `Detail="removed invalid paths"`。
- **影响**：GUI 向用户谎报已清理，无效条目仍在——违背项目自身「不伪造 PASS」红线。
- **验证**：新增定向用例实测——`CleanEnvVarPath` 后 PATH 逐字节不变，`CleanAllInvalidEnvVars` 仍报 `cleaned`（用例 FAIL 即复现）。
- **修复**：让 `cleanEnvVarPath` 回传 `changed`，批量入口据此填 `Action`。

### F-02（P1，上游）`bugx init` / `bugx install` 在 npm 安装下永远失败

- **位置**：`engine_installer.py:869-888`（守卫）× `bin/bugx.js:56`（启动器设 `BUGX_ASSET_ROOT`）
- **根因**：npm 包布局下 `parents[2]/core` 恰等于 `BUGX_ASSET_ROOT` 指向的 `<pkg>/core`，使「拒绝从项目源码树安装引擎」守卫**恒真** → 唯一合法来源被自己的守卫拦死。
- **影响**：全新 npm 安装的 BugX 开箱即不可用；用户须自行猜到 `--force`。本次审计即靠 `--force` 才得以初始化。
- **修复**：复用同文件 `_asset_candidates()` 第 295-298 行**已有**的「源码树判定」（`pyproject.toml` + `scripts/bump_version.py`）来排除 npm 布局。

### F-03（P1，上游）`tools-kb.md` 过期硬阻断启动，且与完整性守卫互斥

- **位置**：`pre_phase.py:949-951`（硬门禁）× `tools_kb.py:27`（KB 路径硬编码）× `engine-integrity.json`（`tools-kb.md` 受哈希冻结）
- **根因**：协议要求「过期即重搜并**回写本库**」，但该文件被引擎完整性哈希冻结，`doctor --repair` 会用包内旧副本回滚 → **改了就破坏完整性并被回滚，不改就过不了门禁**，无受支持通路。
- **影响**：2026-09-14 批次条目满 30 天后，任何新安装都无法完成 `pre`，即无法启动审计（本次即受阻）。包内与全局副本 SHA-256 一致，证明过期日期系上游随包发布。
- **修复**：过期降级为 `DEGRADED` 告警（对齐其它探针三选降级），仅格式不可解析保持硬失败；或将 `tools-kb.md` 移出完整性冻结范围；或提供 `--kb`/`BUGX_TOOLS_KB` 覆盖入口。

## 五、结论

1. **四个 P0 都是「防线被绕过」类缺陷，而非普通功能错误**：
   - F-09 Lua 沙箱**加固错了表**（改 `package.loaders` 字段，而 `require` 读注册表 `_LOADERS`）；
   - F-12 `.part` **不按 URL 分代**，让跨 URL 续传产出混合文件并被 TOFU 永久固化；
   - F-28 官方一等公民（Lua 插件）与 CLI 命令的组合**直接 panic**；
   - F-37 CI 的两次 checkout 布局让**签名作业必然中止**，且顺带废掉 F6b 的缓存投毒防线。
2. **两个信任根问题（F-37/F-38）值得最优先处理**：一个让签名产不出来，一个让私钥对
   `npm ci`/`gem install` 可见。两者都**不是理论风险**——F-37 已用上游真实源码证实删除机制，
   F-38 的作业级作用域就在文件里。且**同仓库已有正确模式可复用**（`sign-manifests.yml` 的
   步骤级 `env` + `umask` + `trap`），修法成本低。
3. **F-01 是本轮唯一已修复项，且它推翻了一个既有结论**：HANDOFF 记载第六轮「验证全绿」，
   但未提交的票 44 改动使 `internal/gui` 整包测试 606s 超时——**任何 CI 的 `go test ./...`
   都会变红**。这提示「未提交工作未过门禁」是比代码缺陷更易被忽略的风险面。
4. **多个缺陷同属「同产品内两条路径语义相反」**：F-05（CLI 有 force 守卫、GUI 无）、
   F-06（两个 `"all"` 语义分叉的清理绑定）、F-24（三条哈希接受路径不一致）、
   F-32（六处 `SetNoEnvWrite` 漏两处）、F-52（两条 Exec 腿有 `--`、connect 腿无）。
   这类缺陷的共同修法是**收敛到单一实现 + 加源码级守卫**（见方案 F-32 的建议）。
5. **F-44 揭示了一个系统性缺口**：CI 从不运行前端测试、也不跑 `-race`，
   这意味着本轮发现的多个缺陷（F-01 死锁、F-39 替换模式、F-40 重入）**都没有自动化防线**。
   补门禁的收益高于修单个缺陷。
6. **审计纪律**：F-03（上游 tools-kb 门禁）无法绕过时，本轮**明确降级到手工流程并如实登记**，
   未以任何方式伪造门禁通过；F-02 使用的 `--force` 是上游错误文案自身推荐的显式通道；
   F-31 的宿主 PATH 写入事故由 Worker 回滚并经主 Agent 独立复核。全量 50 项发现中，
   **仅 1 项已实施修复**（F-01），其余均以「定位 + 证据 + 方案」交付，未擅自改动被审计代码。
